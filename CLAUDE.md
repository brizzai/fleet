# fleet

> This file provides context for AI-assisted development with Claude Code.

TUI tool for managing multiple Claude Code and OpenAI Codex sessions in parallel using tmux.

## Tech Stack
- Go 1.26+, Bubble Tea v2 + Lip Gloss v2 (`charm.land/.../v2`), `charmbracelet/x/vt` (drawer's live terminal), tmux, SQLite (WAL mode)

## Commit Convention
Use [conventional commits](https://www.conventionalcommits.org/). Version is auto-computed from commits:
- `fix: ...` → patch (v0.1.0 → v0.1.1)
- `feat: ...` → minor (v0.1.0 → v0.2.0)
- `feat!: ...` or `BREAKING CHANGE: ...` → major (v0.1.0 → v1.0.0)
- `chore:`, `docs:`, `refactor:`, `test:`, `style:` → patch
- Scopes are optional: `fix(hooks): ...`, `feat(ui): ...`

## Changelog
- Each PR adds a fragment file: `changelog/unreleased/<name>.md` with `type:` frontmatter (added/improved/fixed/changed/removed)
- **Keep fragments concise: 1–2 sentences, lead with the user-facing change.** No implementation detail, marketing tone, or exhaustive sub-points — a user skimming the release notes should grasp it at a glance. e.g. "Status updates now respond in ~150ms instead of up to 2s."
- **Voice — fun via honest specificity, not hype.** Fragments render in-app (Ctrl+K → "Release Notes", which formats `` `code` `` + `**bold**`), so write for a reader: open each bullet with a **bold 2–4 word headline** so a release skims in one pass; write in second person ("You can now…", "Sessions now…"); name the annoyance you killed ("…instead of a cryptic 'Operation not permitted'"); numbers over adjectives ("~150ms instead of 2s"); `code`-format keys/commands/paths (`Ctrl+K`, `~/Documents`); one idea per bullet; ban hype words (seamless, powerful, delightful, blazing). Full guide + examples: `changelog/README.md`.
- Add `highlight: true` to a fragment's frontmatter to also surface it in the in-app **What's New** reel. The item still renders in its normal type section; the flag *also* copies it into a `### Highlights` block that leads the release (emitted by `prepare-release.yml`). Reserve for changes a user would be glad to discover — most fragments are not highlights.
- **Never decide `highlight` on your own — always ask.** When you write a fragment, ask the user (via the `AskUserQuestion` tool) whether it should be a highlight, and give a recommendation with your reasoning. A highlight *leads the release* in the What's New reel, so it's an editorial call about what deserves the user's attention — not a property of the diff, and not something you can infer from how big the change felt to implement. Default recommendation is **no**: most fragments are not highlights. Ask even when you're confident, and ask on the way in (when writing the fragment), not after the PR is up.
- CI checks for fragment presence; comment `/no-changelog` to skip
- At release time, fragments are merged into CHANGELOG.md and deleted

## Design System
**Read `docs/design-system.md` before any UI work.** It is prescriptive, not advisory.

The short version: **focus > selection > mode**, in that fixed order of visual weight, and a **mode never fills**. A background fill is the scarcest thing in the UI — spend it on the cursor and the caret. Roles live in `internal/ui/design.go` (`SelectionPill`/`SelectionBand`/`SelectionMarker`/`ModeOn`/`ModeOff`/`FocusCaret`/`PrimaryAction`/`NewTextInput`); build a style inline and you are inventing a fourth dialect. `Background(ColorAccent)` outside that file **fails the build** (`TestAccentFillIsConstructedInOneFile`), and so does a mode indicator that fills (`TestModeNeverFills`).

The doc also settles the three questions that kept getting answered ad hoc: pill vs band (sized by the filled region, ~40 columns), which presentation tier a new surface takes (full-screen / centered overlay with `dimBackdrop` / row-anchored dropdown with none), and whether a tab is a mode or a selection (**does switching it move the keyboard?**).

Styles in `styles.go` are declared **bare** and constructed **only** in `ApplyPalette` — an initializer alongside would be a second copy, and a style built in only one of the two silently keeps default-pink under every other theme.

## Conventions
- Tmux session prefix: `fleet_` (agent sessions); drawer shells use a distinct `fleetsh_` prefix — intentionally not a prefix of `fleet_`, so shells never leak into agent-session enumeration (`tmux.ListSessions`)
- Session ID format: `<8hex>-<unix_timestamp>`
- SQLite DB: `~/.config/fleet/state.db`
- `fleet worktree <branch>` (alias `wt`, `cmd/fleet/worktree.go`): the TUI's `w` key as a CLI command — create the worktree, copy `.claude/settings.local.json` + `copy_files` entries, start a session. Flags: `--base` (defaults to `git.GetDefaultBranch`), `--path` (defaults to cwd), `--agent` (defaults to `default_agent`; **validated explicitly** — `agent.Parse` falls back to Claude for anything unrecognized, so a typo would silently launch the wrong agent), `--account` (Claude account email; defaults to whatever `account_strategy` picks. **Validated explicitly against the configured accounts** — an unknown name errors rather than falling back, since the cost of a typo here is billing the wrong subscription. Rejected alongside a non-Claude `--agent`, which would silently ignore it), `--no-session` (print only the worktree path, so `cd "$(fleet worktree foo --no-session)"` composes; conflicts with `--agent`, `--account` and `--prompt`), `--prompt`/`-p` (the agent's first message — `-p -` reads stdin, so `gh issue view 242 | fleet wt fix-242 -p -` works; conflicts with `--no-session`). An explicitly **empty** `-p` is rejected rather than ignored: `-p "$(gh issue view 999)"` on a missing issue expands to nothing, and silently starting a promptless session reads as a broken flag (`fs.Visit` is what separates `-p ''` from an absent `-p`). Flags parse on **either side** of the branch (a loop peeling one positional per `fs.Parse` — a single Parse stops at the first positional and would reject `fleet worktree foo --no-session`). It resolves to the **main** worktree (`git.GetMainWorktreePath`) before creating, so running it from inside `repo-foo` yields `repo-bar`, not `repo-foo-bar` — same as pressing `w` on an origin header. It calls `debuglog.Init()` first: `debuglog.Logger`'s fallback writes to **stderr**, and the provider/`Session.Start` log at Info, so without it the command spews slog lines over the user's terminal (`fleet add` still does).
- Initial prompt (`Session.InitialPrompt`, set by `fleet worktree -p` and by `fleet send` waking a suspended session): the agent opens **already working on it**, because all three agents take a first message on their own command line (`claude "<p>"`, `codex "<p>"`, `opencode --prompt "<p>"`, each also valid alongside resume/fork). The text never enters that command string. `tmux.Session.Start` *types* the launch command into the pane's shell, so an embedded prompt would be parsed by that shell — `$(...)` and backticks would execute, and a newline would end the command early. Instead the prompt rides `tmux new-session -e FLEET_INITIAL_PROMPT=<raw>` (`agent.PromptEnvVar`, set in `sessionEnv`), which no shell parses, and the command carries only `"$FLEET_INITIAL_PROMPT"` — one argv element whatever it contains. Two tests pin this: `TestBuildLaunchCmdNeverEmbedsPromptText` and `TestInitialPromptTravelsInEnvNotCommand`. Quoting only settles the **shell**; the agent's own argv parser is a second parser, and it reads a leading `-` as an option and *exits* — leaving a live session at a shell prompt with the message gone. So the prompt sits behind a separator that ends option parsing: `-- "$FLEET_INITIAL_PROMPT"` for Claude/Codex, `--prompt="$FLEET_INITIAL_PROMPT"` for OpenCode (with a space, yargs reads the *value* as a fresh option). `fleet send` explicitly promises a message may start with a dash, and the suspended-wake path routes that message through here. **One-shot**: every launch path clears it on success via `consumeInitialPromptLocked` — `Start`, `Restart` (the `r` key, and the idle-suspend wake) and `RespawnClaude` all build from `buildAgentCmd` + `sessionEnv`, so a path that forgets silently re-asks the original task. Never persisted, or it would replay on every app restart. Kept on a *failed* launch so a retry still carries it.
- `fleet send <session> <message>` (`cmd/fleet/send.go`): messages a session from the shell — the half of a session's lifecycle the CLI couldn't reach. `<message>` is every argument after the selector, joined; a lone `-` reads stdin. Flags must come **before** the selector (unlike `fleet worktree`, whose flags parse on either side): a message is free-form prose that can start with a dash, and the flag parser silently eating words out of what the agent receives is worse than requiring flag-first. Delivery is `load-buffer` + `paste-buffer -p` + a **separate** `send-keys Enter` (`tmux.PasteAndSubmit`), not `SendLiteralKeys`: literal keys make every newline its own Enter, submitting a multi-line message a line at a time, and the Enter must land after the paste's closing bracket to read as "submit" rather than as pasted text. Selector tiers, most precise first: `@0`-`@9` slot, exact id, exact title, workspace name, git branch (injected as `branchOf` so the resolver stays pure — it's the only tier that shells out, hence last of the exact ones), id prefix, title substring. A tier matching several sessions is an **error listing them**, never a fall-through to a vaguer tier that happens to match one.
- `fleet send` guards, in order — each exists because the pane is a *typing* surface, not an API: **suspended** → wake it (`Restart()` with the message as `InitialPrompt`, then persist the new `tmux_session`, status **and any conversation id `adoptResolvedLaunchID` just healed** — the TUI's worker re-persists that a moment later, but a one-shot CLI process exits first and would recompute and discard the heal on every wake); **no tmux / `pane_dead`** → refuse; **pane back at a shell prompt** (`shell.IsShellCommand` over `tmux.PaneCurrentCommand`, after an explicit `RefreshSessionCache` since the TUI's tick isn't running) → refuse, because `/exit` or a crash drops the pane to a shell where the message *runs as a command* — deliberately **not** `-force`-able; **waiting** (`session.PaneIndicatesWaiting`) → refuse unless `-force`, since text typed into a numbered menu is discarded and its Enter confirms the highlighted option.
- `fleet send` startup handling — a session is launched by *typing* the agent's command into a fresh pane, so "not ready" and "exited" look alike from outside and the naive one-shot read got both wrong. Two separate waits, because one signal can't cover it: `waitForAgentInPane` polls up to `agentStartupGrace` (10s) for the pane to stop reading as a shell (measured process-start ranged **0.6s–7.4s**; under-waiting made `fleet wt … -p -` immediately followed by `fleet send` fail with a flatly false "has exited", and that branch isn't `-force`-able). That only proves the *process* started — the TUI then spends **~2.4s** painting, and anything written to the pty in that window is discarded. No signal distinguishes it: the process name has already flipped, and waiting for the pane to *settle* fires ~2s early (measured: settles at 783ms, input box renders at 2972ms) because the screen sits static mid-startup. So readiness is never predicted — `confirmDelivered` checks the **outcome**, polling the pane for the message's whitespace-squashed first line (or Claude's `[Pasted text` placeholder, since a multi-line paste is collapsed and never appears verbatim) and reporting an honest failure if it never lands. **No auto-retry** — a re-paste on a false negative submits twice. Costs ~65ms on a live session; a message under 6 chars skips the check, since a short needle would match by coincidence. That last check reads the **pane, not the hook**: granting a permission fires no hook, so the stored hook status stays `waiting` long after the user answered — stale in exactly the direction that would block legitimate messages. It returns false for OpenCode (no structural detector for its UI). Waking a suspended session prints a note that an already-open TUI still shows it suspended: the TUI reads SQLite once at startup and only ever *adopts* unseen rows.
- `fleet skill <install|uninstall|status>` (`cmd/fleet/skill.go`, `internal/skill`): installs the [Agent Skills](https://agentskills.io) `SKILL.md` that teaches a coding agent to drive fleet's CLI. **Opt-in, unlike hook injection** — hooks are load-bearing (no status without them), a skill is a convenience, and it costs its description in the context of *every* session in every repo, so it stays the user's call. Discovery is `fleet -h` (worded at agents: "run `fleet skill install` yourself, it never prompts") plus a `tipOnce` in the TUI. **Never prompts and never reads stdin**, so an agent can install it for itself in one call. Writes **two roots, not four**, because the agents overlap: `~/.claude/skills` (Claude Code; also read by OpenCode and Cursor) and `~/.agents/skills` (Codex, Cursor, OpenCode). Neither root alone suffices — Codex reads only `.agents/skills`, Claude Code only `.claude/skills` — and Cursor/OpenCode map to `.agents/skills` so either one installed *without* Claude Code still lands somewhere it reads. Agents sharing a root share one write (`run` dedupes by path), so three selected agents don't race three writes at one file. **Selection is by name, the operation is by path, and the report must follow the path** — `run` acts in a first pass and reports in a second, so an agent the user *didn't* select whose file was written or deleted anyway (because a selected agent shares its root) reports what really happened, tagged `SharedWith` and rendered `(shared with codex)`. Reporting it as skipped told an OpenCode user their skill was untouched in the same breath as deleting it. Read-only `Status` deliberately does **not** disclose sharing: nothing changed, so there's no side effect to own up to, and disclosing it would make an explicit `-agent` filter look ignored. Frontmatter is restricted to **`name` + `description`**: that's the intersection every target accepts (Claude Code's packaging validator rejects unknown keys outright), and `name` must equal the install directory or the skill silently never loads — `TestFrontmatterIsPortable` pins both. Written via temp-file + rename because **Claude Code watches skill dirs for live changes**, so a partial `SKILL.md` can be read mid-write. Install defaults to **detected** agents; uninstall and status default to **all** (the copy worth removing or finding usually belongs to an agent the user has since uninstalled), and every verb honours `-agent` — `status` silently dropping a valid filter would be the same swallowing `resolveAgents` rejects for typos. Detection is binary-on-PATH, plus a config dir **only where fleet never creates one**: `~/.cursor` counts (Cursor installs its `cursor` shim only on request), `~/.codex` and `~/.config/opencode` count (their injections are `LookPath`-gated for exactly this reason), and **`~/.claude` explicitly does not** — `NewHome` calls `InjectClaudeHooks` ungated and it `MkdirAll`s the dir, so every fleet user has one whether or not Claude Code exists. Trusting it installed a Claude skill for Codex-only users. A skipped agent's printed reason re-checks detection rather than assuming: telling a Cursor user Cursor isn't installed, when they merely passed `-agent claude`, is a false claim about their machine. The TUI's tip samples `skill.AnyInstalled()` **once in `NewHome`**, not from the tip's `active()` — that runs on the ~2s Update tick, where filesystem calls don't belong.
- External-session adoption: the TUI reads sessions from SQLite exactly **once**, at startup (`loadSessions`), so a session created by another fleet process would be invisible until restart. `maybeAdoptExternalSessions` (heavy worker pass, self-throttled to `adoptSweepInterval`=5s) diffs the table against the cycle's snapshot via the pure `unknownSessions` and sends `adoptSessionsMsg`; `handleAdoptSessions` re-checks `sessionByID` (the snapshot is taken at cycle start, so the Update goroutine is the only authoritative dedupe point) then mirrors `handleSessionCreateResult` minus `SaveSession`/analytics. **Adoption only** — rows deleted elsewhere are never dropped. Unlike a session the user just created, an adopted row arrives on a timer, so the cursor must not move: it's captured with `targetForCursor()` and restored by identity via `target.find` after the rebuild. No resurrection risk — `deferDelete` deletes the SQLite row immediately, ahead of the 5s undo window.
- Sessions grouped by git repo root in sidebar with tree lines (├─/└─)
- Status: Running, Waiting, Finished, Idle, Error, Starting, Suspended
- Status icons: ● (running/finished), ◐ (waiting), ○ (idle/starting), ✕ (error), · dim (suspended — same dot as idle; dim style + "suspended" label distinguish it)
- Agent glyph: each session row shows a dim, monochrome per-agent sigil between the status dot and the title — `✻` Claude, `◇` Codex, `△` OpenCode (`agentGlyph` + `AgentGlyphStyle` in `sidebar.go`/`styles.go`); all are width-1 glyphs from well-covered Unicode blocks (Dingbats / Geometric Shapes — same block as the status dots) so they stay aligned in base mono fonts; identity is carried by shape so the status dot keeps sole ownership of color; empty/legacy `Agent` falls back to Claude
- Keybindings: j/k nav, `Shift+↑/↓` jump to prev/next group header (origin or checkout — from a session row the nearest header above is its own checkout header, so `Shift+↑` surfaces the current group before climbing out; clamps to the first/last row when no header remains, so it doubles as top/bottom), Enter attach, Space jump to next waiting/finished, a new session (instant, repo-scoped, default agent), A new session with agent picker (Claude/Codex/OpenCode), n new session (any repo, path autocomplete), w new worktree session (base branch + new branch; works on a session, checkout header, or origin header — an origin header bases the new worktree on the group's main clone), F fork to worktree (Claude-only), d delete (scope follows cursor: session = that session; worktree header = sessions + git worktree remove; repo header = forget repo from fleet, folder untouched; empty repo header = unpin; origin header = forget the whole group, checkbox-gated), u undo delete (5s window), r restart (confirm, configurable), R rename, m mark session as unread (idle→finished), z snooze (scope follows cursor; `z` again on a snoozed row wakes it), e editor, p open PR in browser, Y quick approve (waiting sessions), `.` context menu for the row under the cursor (session rows include "Move to Account…"), / filter, Ctrl+K command palette, `t` my tickets, `` ` `` toggle terminal drawer, S settings, W what's new (release notes reel), X dismiss on-screen tip, ! report (wrong status / bug / feature picker, captures a status snapshot on keypress), ? help, ctrl+c quit
- Non-Latin keyboard layouts (issue #239): a terminal reports the **character the layout produced**, not the key pressed, so under a Hebrew layout the physical `j` arrives as `ח` and *every* letter command falls through `handleKey`'s `switch msg.String()` silently. `internal/keylayout` holds one chart per layout (Hebrew, Russian, Arabic, Greek) written in the **US-key → produced-character** direction — the direction a keyboard chart reads, which is the only practical way to review it against one — and inverts them. **The safety rule lives in `buildToUS`, not in discipline: an entry survives inversion only if the produced character is non-ASCII.** Every fleet binding is ASCII, so a hit can never shadow a key the user actually pressed; that's why callers need no "is this already bound?" check and why a Latin layout (AZERTY/QWERTZ/Dvorak) is provably untouched. The cost is that positions emitting ASCII on their own layout aren't remapped (Hebrew `q`→`/`, Greek `q`→`;`), and Arabic `b` can't be (it produces the two-rune ligature `لا`) — all three are asserted as *documented* gaps, so a real omission still fails the test. `normalizeKey` (`internal/ui/keylayout.go`) rewrites **both `Code` and `Text`**: `Key.String()` returns `Text` verbatim when non-empty, and `String()` is what every switch here matches on, so setting only `Code` would pass a unit test and still dead-press in the app. Ctrl/Alt chords are skipped — they already carry a Latin letter on every layout. Two call sites, each placed so a text input is **structurally** out of scope rather than merely avoided: in `handleKey` *below* the modal/launchpad/focus/filter/drawer branches, and in `routeToModal` for the 8 dialogs owning no `textinput` (`TestNormalizedDialogsHoldNoTextInput` parses `routeToModal` for `Update(cmdMsg)` calls and fails if a text-owning dialog joins them; `TestFindTextInputDetects` is its positive control, since a blind detector would make it pass unconditionally). Deliberately never reaches `forwardKeyToPane`/`handleFocusKey` — those push `msg.Text` into tmux, so a Hebrew user's shell must receive Hebrew. **One exception, and it's a symmetry fix, not a convenience:** `handleTypingKey` matches the drawer's *chrome* on the US position (`switch normalizeKey(msg).String()`) because it intercepts keys *above* the remap — without it, Russian `ё` (which sits on the backtick key) would open the drawer and then be typed into the shell, with nothing left that closes it. Only the chrome comparison is remapped; everything forwarded stays literal. Cost: `ё` reaches the shell only via `Ctrl+G` full attach, the same trade already made for `Ctrl+T`/`Ctrl+W` (`TestNonLatinKeyClosesDrawer`). **Caseless scripts (Hebrew, Arabic) send identical bytes for `ש` and `Shift+ש`** — the shift isn't in the byte stream and no table can recover it — so the uppercase commands (`A R S W X Y D F`) stay unreachable by their letter there; `Ctrl+K` and `.` are the layout-independent escapes. Russian/Greek carry capitals, except Greek `W`: shift+w and shift+s both emit `Σ` and `S` (settings) owns it.
- Terminal drawer (`` ` `` key): a collapsible panel holding plain non-agent "shells" (dev servers, log tails, scratch commands), scoped to the selected repo/worktree. - Idle-session suspend (memory-pressure hibernation): a full fleet of `claude --resume` processes (~400MB each) can exhaust RAM/swap and get the shared tmux **server** OOM-killed — taking every session down at once. The background worker's heavy pass runs `maybeSuspendIdleSessions` (throttled ~20s via `lastSuspendSweepAt`): it probes `perfwatch.MemoryPressure()` (platform-split: macOS `kern.memorystatus_vm_pressure_level`, Linux PSI `/proc/pressure/memory` — better OOM signals than "Pages free") plus free swap, where low swap escalates to critical per platform rules (`SwapEscalatesPressure`: trusted outright on macOS's demand-grown swap; on Linux only corroborating a PSI warning, since fixed partitions sit partially used on healthy boxes) and hibernates the most-idle sessions. **Only `StatusIdle` sessions** are ever auto-suspended (never running/waiting/starting/finished). - **The core move is fetching one step earlier than you'd expect.** If fleet materializes the ticket at worktree-creation time, the agent never needs to know the tracker exists — which is why fleet ships no tracker skill and no sidebar badge. It hands over content, not instructions.
- **The layering is domain / providers / router, and the domain package imports no provider** — that's what keeps it acyclic. `internal/ticket` owns everything that was never tracker-specific: the `Provider` interface, `Ticket`/`Document`/`Result`/`Account`, branch naming, the seeded prompt, the image downloader, the keychain `Store`, `ticket.md`, the `meta.json` ledger and `Materialize` itself. `internal/linear` and `internal/jira` are clients that implement `Provider` and nothing more. `internal/ticketing` is the only ticket package the UI and `cmd/fleet` import; it holds the registry and is the one place that knows there is more than one tracker.
- **A provider is a zero-size value over package-level state, not a struct with fields.** That state has to be reachable from `Available()`, which the Bubble Tea Update goroutine calls and which therefore may not do any work — two atomics behind a package var is what makes that free, and an instance the UI would have to find first is not. Same reason `Keys(repoPath)` is two small file reads.

- Auth resolves per provider, env first, both cheap. **Linear**: `LINEAR_API_KEY` → fleet's own store; two credential kinds differing in exactly one place — `authHeader()` — where a personal API key is sent **raw** and an OAuth access token takes `Bearer` (sending either in the other form reads as a rejected credential; `TestAuthHeaderFormDiffersByKind`). **Jira Cloud**: `JIRA_SITE` + `JIRA_EMAIL` + `JIRA_API_TOKEN`, **all three or none** (a site with no token is not a credential, and falling back to the store while `JIRA_SITE` is exported would authenticate against a different site than the variable names) → fleet's own store; one kind, `Basic base64(email:token)` — **not** a bearer, which is rejected exactly like a wrong password with nothing saying the *form* was the problem.
- **A search term is escaped for TWO parsers, in order** (`escapeJQL`): Lucene first (backslash-prefix its reserved set), then the JQL string literal (double every backslash, escape `"`). Quoting alone is not enough — Lucene parses the *contents* of the literal for a `~` comparison, so `fix (login` typed into the New branch field, which fires a search at three runes, came back as a 400 the dialog reported as "Jira: unavailable". Half a branch name is not evidence that the tracker is down.
- **Jira is Cloud only**, and that is enforced by the API version rather than the hostname. REST v3 is what serves ADF and exposes `/rest/api/3/search/jql`; Server and Data Center speak v2, return wiki markup, and take a bearer PAT — a second fetch path and a second auth story for a product fleet cannot test against. `NormalizeSite` therefore accepts any host with a dot (Atlassian now serves Jira Cloud on customer-owned domains, and refusing those would refuse an ordinary site) and appends `.atlassian.net` only to a bare tenant name. A Server site fails `VerifyCredential` with a 404, which the Connect dialog turns into "fleet supports Jira Cloud only" — the one place that diagnosis can honestly be made.
- **Error classification is per-tracker and the two are opposites, so each has a test saying which way round its API works.** Linear answers an unknown issue with **HTTP 200** and an `errors[]` entry whose own `extensions` carry `statusCode 400` (`TestGraphQLErrorClassification`); reading the status alone would file "no such issue" as a generic failure. Jira answers with real status codes (`TestErrorClassification`); reading the body first would do the same in reverse. Jira's 404 means "not found, **for you**" — it deliberately does not distinguish a missing issue from one the credential may not see, since telling an unauthorized caller which keys are real is a leak.
- The store is first-usable and **per provider**, mirroring `clipboardCopyCommandFor`: macOS Keychain (`security`) → `secret-tool` (libsecret) → `~/.config/fleet/<provider>.json` at 0600. `ticket.Store{Service, Label, FileName}` carries the names on a value, which is what makes the second provider a construction rather than an edit — the previous version hardcoded `fleet-linear` in three places and a fourth that disagreed (the secret-tool branch ignored the service it was handed, so the test seam silently did not work on Linux). **The secret never touches argv**: `security -w <value>` and `-X <hex>` both work and both publish it to every `ps` on the machine, so `Save` feeds it on **stdin twice** — `security ... -w` implements an interactive "type it again" prompt and does not care that stdin is a pipe. Verified against a live keychain. **That prompt reads through `readpassphrase(3)`, whose buffer is `_PASSWORD_LEN` = 128 bytes, and past it `security` stores the first 128 and still exits 0** — no failure, no warning. The record then reads back as a JSON prefix that cannot parse, the load reports "no credential", and the user reconnects on every launch with nothing saying why. It split the user base in the worst possible way: an API-key record is ~85 bytes and fits, so the paste path looked perfect while **every OAuth login was destroyed on every write**. So the record is **chunked** at 96 bytes each, chunk 0 carrying a `<total>:` header so a torn write reads as *absent* rather than as a short credential, and old chunks are deleted before a write so a shrunk record leaves no tail. The chunk writer must **never** build its stdin with `append(data, '\n')`: `data` is a slice *into* the record, so that writes into its spare capacity — the first byte of the next chunk — and it corrupted every multi-chunk write while each call still returned success. `TestKeychainStoresRecordsPastThePasswordBufferLimit` pins 129 (the first byte over the cliff) and the multi-chunk sizes; a round-trip test with a short value passes either way, which is exactly what the original one did. `sanitizeForIssue` redacts `lin_api_*`/`lin_oauth_*`, `ATATT*` **and a bare `Basic <base64>` header** beside `sk-ant-*` — the last one because Jira's token is base64-encoded *away* inside the header, so a prefix rule alone catches only half of it (`TestBuildStatusReportBody_NeverLeaksJiraToken`).
- **Linear ships both auth paths and the user picks.** Browser sign-in is the shorter one; pasting a personal API key is the only one that works over SSH, in CI, where an admin has disabled OAuth installs, and where the user wants read-only or team-scoped access. OAuth is **PKCE, so no client secret ships** — the client ID is public like `projectAPIKey` (`FLEET_LINEAR_CLIENT_ID` overrides). Redirect ports are **fixed** (53682-53684, first free) because Linear matches `redirect_uri` against the app's registered list and an ephemeral port is simply rejected; all three busy, or no browser, returns `ErrOAuthUnavailable`, which is a **routing** answer, not a failure — the dialog points at the paste path. The `state` check runs **before** the code is touched (`TestOAuthStateMismatchRejected`): the callback is a fixed loopback port, so anything on the machine can reach it during the window. Access tokens last **24h**; `credential()` renews at a 5-minute margin, serialized by `refreshMu` — without it a ticket with a dozen screenshots starts a dozen downloads that each find the token stale and each spend a refresh. A **refused** refresh disconnects (the grant is gone), while an unreachable endpoint does **not** — fleet failing to reach Linear is not evidence against the grant.
- **Jira ships one auth path, deliberately.** Atlassian's OAuth 2.0 (3LO) needs an app brizz would register and own forever, and in many organizations a per-site admin has to approve each install — for a credential a user can mint themselves in two clicks at `id.atlassian.com`. The API token also covers the SSH/CI case Linear needs its paste path for anyway. An Atlassian API token does not expire on a timer, so there is nothing to renew and a rejected one is a revoked one: the honest move is to report it rather than retry.
- **`Available()`, `Resolved()` and `Keys()` are called from the Update goroutine** and therefore touch no network and no keychain — atomics and small file reads. The keychain reads happen once, in `warmTickets()` from `Init`. `Resolved()` is separate from `Available()` on purpose: before the warm finishes, "no credential" is ignorance, not a fact, and anything acting on the *absence* of one (the discovery tip) must wait. `ticketing.Resolved()` requires **every** provider to have warmed, not any — a tip that fires while one is still resolving would offer to connect a fleet that is about to say it already is.
- Repo keys come from `.fleet.json`/`.fleet.local.json`: `{"linear":{"team":"BRZ"}}` and `{"jira":{"project":"OPS"}}` (plural `teams`/`projects` lists append and dedupe; a local singular **replaces** the committed one — see the `.fleet.json` bullet below). Linear also falls back to `team_id` in a committed `.linear.toml`; that file belongs to the CLI fleet no longer uses, but reading one key out of a file someone already has costs nothing, and **`api_key` in the same file is never read** (`TestTeamKeysReadOnlyTeamID`). Jira has no such fallback — no tool writes a per-repo Jira file anyone already has. Gating is on the **set**, not one key — a workspace routinely has several teams and one repo may see branches from both.
- **A ticket that already knows its provider is never re-resolved.** `ticket.Opts` carries `Provider`, and `ticketing.Materialize` prefers it, falling back to `Owner(repoPath, id)` only for a bare identifier nobody has claimed yet (the `fleet wt --ticket` path). Applying the repo gate a *second* time was a real regression: search is deliberately unscoped, so a repo tracking only `BRZ` offers `PRD-45`, and re-resolving that pick refused it **after** the branch was named and the worktree created — with `ticketStatusLine` swallowing `ErrNotConnected`, so nothing on screen said why. The repo gate decides *whether ticket surfaces appear at all*; it is not a rule about which issue you may work on. `ticketStatusLine` no longer swallows `ErrNotConnected` either — at that call site the user demonstrably has a ticket in hand, so it means the credential went away in between, which is the same argument that already applied to `ErrNotFound`.
- **`ticketing` order decides who owns a contested key.** A repo naming `BRZ` as both a Linear team and a Jira project is pathological, but "first configured wins, and the order never changes" is an answer where "whichever the loop reached first" is a coin flip that lands differently between launches. `Owner`/`OwnerIn` resolve by the identifier's key prefix; `Keys` is the deduped union, which is what `LooksLikeIdentifier` and `IdentifierFromBranch` gate on.
- One round trip does everything per provider. **Linear**: `issueFullQuery` carries description, comments, labels, assignee, priority, parent/children, attachments, **and the team's workflow states**, so the optional state write needs no second query — measured at **87 complexity points** against a 10,000-per-query cap. **Jira**: one `GET /rest/api/3/issue/{key}?fields=…` carries the same, with a second call **only** when `comment.total` exceeds the page returned (the newest comment is usually what changes what a ticket means). That call is `orderBy=-created`, not `created` — Jira's `orderBy` is ascending by default, so the plain form fetches the *oldest* page, the exact opposite of the reason the round trip is worth taking. The page replaces the embedded set **only when it is larger** (an issue can embed more than `commentFetchLimit`, and swapping 100 for 50 would lose half of them while looking like a fix), and is reversed back to chronological before rendering so `ticket.md` reads as a conversation in both trackers. Rate limits are generous against roughly 2 calls per worktree, so **no throttling machinery exists** in either.
- **`ticket.Priority` keeps Linear's numbering on purpose** — `0` unset, `1` urgent … `4` low — so the palette's priority gauge and its colour ladder need no translation layer and a Jira row renders identically to a Linear one. `Rank()` exists because the raw number cannot be sorted on: `0` means "not set", so ascending order would float every unprioritised ticket above the urgent ones. Linear's number converts verbatim; **Jira maps by priority NAME, not id** (schemes are per-project, so the default ids 1..5 mean Highest..Lowest only on a site nobody configured), covering `highest|blocker|critical` / `high|major` / `medium|normal` / `low|minor|lowest|trivial`. Anything unrecognized is **None, not Medium**: guessing a middle rank would put it above a real Low, and the list is sorted on this.
- `ticket.StateType` normalizes the state category, and `ticket.SortAssigned` owns the one comparison (**state type → position → priority → the server's order, stable**) so a merged Linear+Jira list is ordered by the same rule as either one alone. Linear supplies a real `StatePos` — the difference between "In Progress" and "In Review" leading the list; **Jira has no position at all**, so it supplies 0 and the tiebreak falls through to priority. Jira has no distinct backlog or triage category either, so both collapse into Unstarted — honest rather than lossy, since a Jira "To Do" really is one bucket.
- The one mutation. **Linear** resolves the team's started state by **type**, against a position-sorted list (`TestStartedStateResolvesByTypeAndPosition`) — type so it works on a team whose started state is called "In Dev", position because a real team has several started states and the lowest is what a human means by "I'm starting this". **Jira** has no position and every in-progress-ish status shares the `indeterminate` category, so `startedTransition` prefers the exact name **"In Progress"** (Jira's own default) and otherwise takes the first indeterminate transition in the workflow's own order — picking wrong would move a fresh ticket straight to review. It costs a second round trip, unlike Linear's, because available transitions depend on the issue's current status and the caller's permissions and cannot ride along with the fetch. Fires **only on create-from-ticket** (config `ticket_start_state`, default true; the pre-Jira `linear_ticket_start` is still read when it is unset), never when a later session opens in an existing worktree — by then a human may have moved the issue on. `meta.json` records `state_write` so it stays exactly-once, and now records `provider` too: two trackers can land different issues in one `.fleet/ticket/<ID>/`, and a Linear write says nothing about whether the Jira issue of the same key has been started.
- **Extensions come from the BYTES, and only from the bytes.** Linear's default alt text is literally `image.png` and its upload URLs carry no filename, so a real PNG would land unnamed and unextensioned — and an agent's file-read tool dispatches on extension, making a perfectly downloaded screenshot unreadable. `detectExt` sniffs magic bytes (`http.DetectContentType`) and takes no filename argument at all. It used to short-circuit on a recognized extension, and `fetchImage` used to read `Content-Disposition`/`Content-Type` first — which meant that for Jira, where the alt *is* the filename and both headers are always sent, **the sniff never ran**: a 200 carrying an HTML interstitial for `screenshot.png` landed on disk as a `.png`, past a check whose whole stated purpose was to stop that. The one exception is **SVG**, which Go's sniffer cannot name (`<?xml` reads as `text/xml`, a bare `<svg>` as `text/plain`), so a header saying `image/svg+xml` is honoured *only* when the body sniffs as XML or plain text — an HTML body is refused whatever the headers claim (`TestBytesBeatHeaders`).
- **Images are declared by the provider, never scraped from the rendered markdown.** A `Document` carries `Images []Image` and writes `![alt](fleet-image:<n>)` placeholders into its body; `collectImages` downloads and rewrites them. The indirection exists because the two providers find their images in incompatible ways and neither can write a final path — the on-disk name is only known once the bytes arrive. Matching is on the **whole link target including the closing paren**: `fleet-image:1` is a prefix of `fleet-image:10`, so matching the bare token would let image 1 succeeding rewrite half of image 10's link (`TestCollectImagesIndexesAreNotPrefixes`). A placeholder whose download failed or hit a cap degrades to `(image: alt — not downloaded)` rather than a dangling link, because an agent told to open every file in `images/` will try.
- **Jira downloads every `image/*` attachment, not only the referenced ones**, and that is forced by Atlassian rather than chosen. An ADF media node's `attrs.id` is a Media Services file id and is **not** the attachment id the REST list is keyed by (JRACLOUD-96383/96384 are open requests to add the mapping); alt text is the only bridge and Jira frequently writes none. Inline-only matching would silently drop the screenshot on exactly the bug reports that are mostly screenshot. Everything is listed under `## Attachments`, inlined where a media node resolved and marked `(shown above)` where it did. **Two indexes, because they answer two questions**: `## Attachments` looks up by **attachment id**, since one issue can carry two files both called `image.png` and a name-keyed map collapsed them — both resolved to the second, the first became unreachable, and one screenshot rendered twice while the other was never downloaded, on exactly the screenshot-heavy bug report this branch exists for. A media node has only the filename to go on, so `byName` holds a **queue** and each node claims the next unclaimed index, falling back to the first once they are all taken (the same image referenced twice must render twice, not degrade). Non-images are **named, never fetched**: an agent cannot read a 40MB video, and pulling a customer's spreadsheet into a worktree unasked is not fleet's call.
- **ADF → markdown is a walker, not an HTML pass** (`internal/jira/adf.go`). v3 serves descriptions and comments as a JSON document tree. `expand=renderedFields` returns HTML, which needs its own converter and loses the structured media references; v2 returns wiki markup, a different markup language to convert and one Atlassian is moving away from. Walking the tree is the only option that also solves the image problem, since media nodes are where inline screenshots are named. `code` is applied innermost and **suppresses** the other marks, because `**x**` inside a code span is literal backtick-asterisk text. An **unknown block recurses into its `content`** rather than dropping — ADF gains node types faster than fleet will track them and their text lives in an ordinary content array underneath. `underline`, `textColor`, `subsup` and `border` have no markdown form and are dropped silently: the words survive, and a marker for "this was purple" helps nobody.
- Image gating is per provider and re-checked at the credential. `Document.Host` is Linear's `uploads.linear.app` or the configured Jira site, compared on `url.Hostname()` — never a prefix or suffix, since a suffix test matches `uploads.linear.app.evil.example` and a prefix test matches it too. `https` only, so the credential never crosses the network in plaintext even to the tracker itself. `ticket.fetchImage` **re-checks the gate on the line that attaches the credential**: a gate one call away from the thing it protects is a gate a later refactor removes without noticing. `imageClient` refuses **every** redirect, because Go strips `Authorization` only across a registrable-domain change and deliberately permits `uploads.linear.app → anything.linear.app`. Issue bodies and attachment records are attacker-influenced content — anyone who can write to an issue fleet later materializes, including through Linear's customer requests and Jira's public service-desk intake.
- Files land at `<worktree>/.fleet/ticket/<ID>/` — inside the worktree so the agent reads them with a relative path and **no permission prompt**, since a prompt on the session's first act renders as `-` waiting, the friction this feature removes. Deliberately **not** namespaced by provider: that would change the path under every worktree that already exists and lengthen the one line of the seed prompt an agent has to act on, to fix a collision that needs a repo tracking both trackers *and* a key shared between them. `meta.json` carries the provider instead. Git exclusion uses `git rev-parse --git-path info/exclude`, **never `--git-dir` + `info/exclude`**: `info` is on git's shared-path list, so a linked worktree's `--git-dir` gives a path git never reads — the entry would look installed and exclude nothing (`TestAddFleetExcludeFromLinkedWorktree` proves it with `check-ignore`). The entry is repo-wide, written once, idempotently, and it is `.gitignore`'s opposite on purpose: `.gitignore` is tracked, so writing it would dirty a fresh worktree and risk committing customer screenshots. The exclude is written **before the first byte**, since a window where the files exist and the exclude does not is a window where `git add -A` sweeps a customer screenshot into a commit.
- Branch names are `brz-3182-<slug-of-title>` (`BranchNameFor`), **not** the tracker's own suggested name — Linear's carries an owner prefix (`alice/brz-3182-…`) and Jira's carries the summary verbatim. Both trackers link a PR by finding the identifier anywhere in the name, so every form links identically; this one matches the convention already on disk. `identifier.go` is one file for both providers because a Linear team key and a Jira project key are the same shape.
- Inference is **key-gated** (`IdentifierFromBranch`). The regex is deliberately loose about the prefix because the *caller* gates on the repo's real keys; ungated it reads `fix-123-thing` as `FIX-123` and `release-2024-cleanup` as `RELEASE-2024`, identifiers for teams that don't exist. The gate is what makes a non-ticket branch cost nothing.
- **Nothing polls, and a prompt is seeded exactly once.** Ticket work is event-driven and one-shot: it happens at **worktree creation and nowhere else** (`w` + a ticket, `fleet worktree --ticket`), so a session added by hand with `a`/`n`/`A` starts empty like every other manually created session. `handleSessionCreate` therefore does no inference at all — it passes `msg.prompt` through untouched. fleet used to infer a ticket from the branch on *every* session creation, plus reuse the already-written `prompt.txt` when `.fleet/ticket/<ID>/` was present. Both re-asked the original task on every session after the first, and the reuse branch never looked at the branch at all, so a worktree that once held a ticket kept seeding it after the checkout had moved on to `master`. A seeded first message is the *gesture* of starting a worktree from a ticket, not a property of the directory. `TestTicketWorkStaysOffTheWorkers` keeps it out of `refreshAllGitAndPR`, whose `workerStallThreshold` (90s) is already sized against ~70s of git + `gh` per repo — and it names **every** ticket package, since the single-name version passed vacuously the moment a second provider arrived. This is only affordable because there is no badge, hence no live state to keep fresh.
- The seeded prompt is a **short pointer that tells the agent not to start** (`TestSeedPromptTellsAgentNotToStart`), stated at the top and bottom because a first message describing a task reads as an instruction to perform it. Line 1 leads with the tracker's name and the identifier before the title: the identifier because it is three surfaces at once (the agent's instruction, the preview pane's prompt strip, and the input to `naming.GenerateTitle`, which cuts at ~50 runes), the tracker's name because it is a fact the agent can act on — it is what makes "look it up yourself" possible when the snapshot on disk has gone stale. It rides `sessionCreateMsg.prompt` -> `Session.InitialPrompt`.
- **Ticket suggestions live in the `w` dialog's existing New branch field, not a new field and not a mode** (`internal/ui/workspace_picker_ticket.go`). The field IS the literal option, so nothing duplicates it and only one thing ever claims Enter. Two rules make that hold: **exactly one highlight, and the caret lives with it** — arrowing onto a ticket blurs the input, typing returns both and keeps the keystroke (`isTypingKey`, borrowed from the snooze dialog, whose "the highlight is the promise" rule this follows); and **shape decides the default, never a mode** — text matching a tracker's identifier shape resolves *in place* (`LooksLikeIdentifier`), prose stays literal with tickets one down-arrow below. *In place* means the field **becomes the branch name** (`applyResolvedBranchName` → `BranchNameFor`) while the highlight stays put; it does **not** mean "only record the ticket". That half was missing at first, so typing `BRZ-3217` fetched the ticket, materialized it and named the session after it — and then created a git worktree literally called `BRZ-3217`, breaking the invariant `pickTicket`'s own comment states, that both ways of naming a ticket end up identical. The rewrite is gated on the field still holding **nothing but that identifier**: the generation counter drops a reply a later keystroke invalidated, but it cannot see a *current* reply for a shorter identifier you paused on en route (`BRZ-321` while typing `BRZ-3217`), which would otherwise drop `brz-321-<slug>` under the cursor and let the rest of the typing land on the end of it. The same check leaves a tail you edited by hand alone. The confirmation line reads **`✓ named from BRZ-3217 · <title>`**, not a bare identifier: it renders in the same place the selectable ticket rows do, so on its own it read as a row you might still need to arrow onto when the naming had already happened — and it is the only thing on screen that explains why the field rewrote itself a moment earlier. `✓` is U+2713, East-Asian-Neutral, so it is always one column — the same width check the priority gauge had to pass. The highlight never moves on its own; a picker that jumps its own selection is the ambiguity coming back through the window. `setSelection` is the single writer of `focus`/`ticketCursor`, enforced by `TestWorktreeSelectionMutatorIsTheOnlyWriter`, because a stray write skips the clamp and renders two selection markers. The footer names what Enter will do and changes as the highlight moves.
- **The dialog is a pure function of what it was handed, never of the registry.** `Show` takes `[]ticketing.Bound` and derives its key union once; `SearchBound`/`OwnerIn` act on that set. Two reasons pointing the same way: the dialog **latches individual providers off** as their credentials are refused (`ticketsOff` is keyed by provider `Kind`, so a rejected Jira token cannot silence the Linear suggestions in the same repo — the two credentials fail independently), so re-deriving would search a tracker it has already given up on; and a dialog whose behaviour depends on process-wide credential state cannot be tested at all. A **fan-out search** that fails latches **nothing**, because it names no single provider. The searching line names the live trackers (`⋯ searching Linear and Jira…`), deduped so a repo tracking two Linear teams doesn't read "Linear and Linear".
- Lookups are **debounced (250ms) and generation-guarded**, never per keystroke. Without the generation counter, typing `BRZ-3182` then editing to `BRZ-3184` lets the slower first reply overwrite the field with the wrong ticket's branch name, which then becomes a real git branch (`TestWorktreeStaleTicketReplyIgnored`). The counter is **monotonic and never reset to 0**, unlike `ConfirmDialog.scanGen` — that one lives on `Home` and never recycles; a per-dialog counter reset to zero would let a reply from a previous open match a new one. `d.loading` is deliberately not used for ticket lookups: it swallows every key but `esc`. The owning provider is resolved **before** the closure fires, so a failed reply can still name the tracker it went to — which is the case where naming it matters most.
- Degradation is structural: no credential, no team or project, rejected key, offline, unknown id, or nothing matching — every case leaves Enter working and the dialog usable (`TestWorktreeEnterAlwaysCreates`). `ErrNotConnected` is the resting state for everyone who never connected and is **never surfaced as an error**; `ErrNotAuthenticated` is, because it names a thing to fix. The sentinels carry **no provider prefix**: they used to read `linear: issue not found`, which the UI rendered as `Linear: linear: issue not found`, so every caller hand-worded its message instead of formatting the error. The provider name belongs to whoever is drawing the line. Once the worktree exists nothing may fail the caller: `Materialize` sits beside `copyClaudeSettingsFile` and `CopyConfiguredFiles` and shares their posture, and a failed fetch costs the prompt, never the session.
- Connect dialogs (`internal/ui/connect_linear.go`, `internal/ui/connect_jira.go`): **separate palette commands, not one chooser** — "Connect Linear" and "Connect Jira" each go straight to the thing they name. A pasted credential is **verified before it is stored** (Linear one `viewer`/`organization`/`teams` query; Jira `/rest/api/3/myself` then `/rest/api/3/project/search`), so "connected" is a fact rather than a hope and a typo is caught while the user is still looking at the field they typed it into. Jira's project list is a **nicety, not a proof**: `/myself` already verified the credential, and a token scoped away from project browsing must not read as a bad token. Both then name the keys the account can see and show the exact `.fleet.local.json` line that turns a repo on — the per-repo step is the one people miss, and `.local` is the right file because team membership is personal and `.fleet.json` is committed. Jira's form has **three fields**, and `Enter` on any but the last **advances rather than submits**: one keystroke meaning two things depending on where you happen to be is how a credential gets submitted half-typed. Only the token is masked — a masked site field is how someone spends five minutes not noticing a typo. Discovery is a `tipOnce` firing when a session's branch matches the generic `<team>-<number>` shape **and** nothing is connected — deliberately *not* `IdentifierFromBranch`, which is gated on keys nobody has configured yet at the moment the tip should fire; a false positive costs one dismissible hint, since the tip only offers and never fetches. Its id stays the literal string `connect_linear` even though it now offers both trackers: that value is persisted in `config.seen_tips` and counted in `config.feature_usage`, so renaming it would re-show a tip every existing user has dismissed and reset everyone's learned count. Only the Go constant changed, to `tipConnectTicketsID`.
- **My tickets is a tab in the command palette, not a new dialog** (`internal/ui/palette_tickets.go`; `t` opens straight onto it, `Ctrl+K` reaches it by cycling), and it is **one merged list across every connected tracker**, not a tab each. The question the tab answers is "what am I meant to be working on", and that does not have a Linear half and a Jira half — the identifiers already say which is which, and `ticketing.Assigned` fans out concurrently and re-sorts the union through `SortAssigned`. A provider that fails contributes nothing and **does not fail the others**: half a list is worth more than an error, and one revoked credential must not empty the tab. The palette already had tabs (`paletteTabOrder`, `cycleTab`), so this is the existing surface rather than a fourth full-screen view — and typing narrows 50 rows, which is why the whole open assigned list is fine here where it would be noise in a static list. **The rows carry the join, which is the only thing this shows that a tracker cannot**: which tickets already have a worktree and what that session is doing. Tracker keys are derived from the identifiers themselves (the prefix *is* the team or project), so it needs no repo config, spans every repo on screen, and needs no idea which tracker a row came from. When several sessions share a worktree the row reports the one that most wants you (`ticketSessionRank`), never whichever came first. Enter jumps to the session if one exists, else opens the ordinary `w` dialog with the identifier prefilled (`PrefillTicket`, `pendingTicketID` consumed exactly once) — so the repo and base branch are still confirmed on the screen that always confirms them, and a ticket becomes a branch name by only one code path. Because the list sorts on priority, priority is **shown**, as a three-cell gauge in a lead column — `▰▰▰` urgent, `▰▰▱` high, `▰▱▱` medium, `▱▱▱` low, and **blank** for no priority, since "low" is a choice someone made and "none" is the absence of one. A gauge rather than a label (`P1`/`!!`) because the list is *sorted* on this key and a sort key you have to read row by row gives you nothing across fifty rows — `▰▰▱` ranks below `▰▰▰` at a glance, `P2` only does once you've read both; it is also the shape Linear's own UI uses. `U+25B0/25B1` are Geometric Shapes (the status dots' block) and **East-Asian-Neutral**, so they are always one column — the obvious alternatives `■ □ · •` are *Ambiguous* width, which some terminals render double and which would shear the column out of alignment; Menlo covers both. `paletteLeadWidth` is **4, not 3**: the gauge fills every cell it is given, so a three-wide column rendered `▰▰▰BRZ-1` with no separator. Colour stops after high (red, then orange; the lower two carry rank by shape in the ordinary dim tone): colouring all four tints nearly every row and the top two stop standing out — and yellow, the obvious third step, already means *waiting* in the sidebar. It rides in a **column of its own, not inside `Name`**, for two reasons: a column can be coloured, and a column can be omitted — and it *is* omitted in the mixed `all` tab, where a lead column no other kind has pushed every ticket title four columns right of every command and worktree. **Both of the tickets tab's dedicated columns vanish outside it**, so `ticketRightColumn` puts state and priority back into the right column there — otherwise a ticket in a mixed list shows nothing but its title. State grouping is likewise tickets-tab-only: a `Todo` header sitting above a run of commands would describe rows it has nothing to do with. Rows are **grouped under the state with a count** when nothing is typed; typing drops the headers and folds the state back onto the row, since nothing else would carry it. The badge column is chosen by **tab, not by kind**: in the mixed `all` tab it is a plain `tkt` label, and in the tickets tab it is **gone entirely** — it is 4 wide because of `cmd `/`repo`/`wkt `, and there it only ever held a one-character dot. The *is this in fleet* answer moved to the **right column**, which was empty in that tab, and is spelled out: `● running`, `◐ waiting`, `· suspended`, blank when there is no worktree (`ticketsTabRight`). This reverses the earlier rule that the status is carried by the dot and never repeated as a word — that was right while the two sat in *different* columns saying the same thing, and wrong once the dot was alone on the far left, carrying two facts (is it here, what is it doing) in one glyph with no legend. Right-column content is **composed in parts, never styled as one string**, and it never takes the fuzzy highlight: the matched indexes belong to the Haystack, and painting them onto fleet's own annotation lights up the wrong runes. While filtering, the headers are gone so the state folds back onto the row **in front of** the join — using `it.Group`, deliberately not `ticketRightColumn`, which also appends the priority and would render the gauge a second time two columns from the first (`TestFilteredTicketsTabDoesNotDoubleThePriority`). Identifiers pad to a common width so titles start in one column. Colour therefore means session status and only that, the same discipline that keeps agent glyphs monochrome. `Haystack` must be exactly `Name + " " + <right column>`: the renderer maps matched indexes back onto those two strings by offset. The palette's name column is budgeted against the widest *right* column rather than a fixed 22-rune cap, which was truncating titles to `Storage opt…` on a terminal with room to spare. - Multi-account (Claude only, `internal/claudeaccount`): several Claude subscriptions, one per session, so a spent 5-hour window on one doesn't stall the fleet. The mechanism is **one env var** — `CLAUDE_CONFIG_DIR` (`claudeaccount.ConfigDirEnvVar`) pointing at a directory that holds that account's own claude.ai login — appended in `Session.sessionEnv()` (session.go), the single chokepoint already feeding `Start`/`Restart`/`RespawnClaude` via tmux `-e`. Each session therefore authenticates **exactly as a plain `claude` in a terminal does**: nothing is layered over anything, so claude.ai connectors, Remote Control and `/api/oauth/usage` all keep working.
- **Why not `ANTHROPIC_AUTH_TOKEN`** (which fleet shipped first and then replaced): it sits at auth precedence 2 and *displaces* the claude.ai login, so every session lost connectors and Remote Control and printed a banner saying so. The `claude setup-token` credential behind it is inference-only, which forced three separate workarounds — it can't name its owner (so accounts were keyed `account-<sha256(token)[:8]>`, and rotating a token minted a second identity that orphaned every session pinned to the old one), it can't read `/api/oauth/usage` (so quota came from a hand-rolled probe that POSTed to `/v1/messages` and read rate-limit headers, spending real quota to measure quota), and it can't be verified (so a refused token scored as *unknown* and won every `least_used` comparison). All three are gone. Measured, not assumed: `CLAUDE_CODE_OAUTH_TOKEN` is worse still — against 2.1.221 with a Keychain login present it is **ignored outright**.
- **Two config dirs hold two independent logins.** On macOS the Keychain service name is `Claude Code-credentials` plus, when `CLAUDE_CONFIG_DIR` is set, the first 8 hex of `sha256(NFC(dir))` — derived by reading the shipped binary and confirmed against a live login (`/tmp/cc-spike-a` → `Claude Code-credentials-5205b77d`, pinned by `TestKeychainServiceIsScopedToTheConfigDir`). That suffix is the whole mechanism. `Account.ConfigDir` is therefore stored verbatim and the path is random (`~/.config/fleet/accounts/<8hex>`), never derived from the email or label — the Keychain item is keyed by the exact path, so deriving it from anything renameable would orphan the login.
- Account dirs are **provisioned on every launch**, not just at add time (`Provision`): `projects/`, `skills/`, `plugins/`, `agents/`, `commands/`, `ide/` are symlinked back to the real `~/.claude`, `settings.json` is **copied** (so fleet's hooks ride along, and so a future per-account setting isn't silently global), and `mcpServers` + per-project `hasTrustDialogAccepted` are mirrored out of `~/.claude.json`. Sharing `projects/` is load-bearing: it holds the transcripts `--resume` replays and fleet reads for auto-naming, and it is what lets a session move between accounts and still resume the same conversation. Per-launch because the user's `~/.claude` keeps moving; a dir that captured its state once would drift into a subtly different environment. Not shared: the credential (the point) and `history.jsonl`.
- Account identity is **read, never guessed**: `claude auth status` reports `email`, `orgId`, `orgName` and `subscriptionType` for a real login. `Email` is the key and it is an actual address. `Store.Upsert` still matches on `OrgUUID` first (`indexOfLocked`), which now means "logging the same subscription in twice updates the existing account" rather than papering over a fingerprint rotation. A **blank org never matches**; a *different* org is a different subscription, never a correction.

- Assignment (`claudeaccount.Select`, the one place strategy lives) via `account_strategy` config: `least_used_weekly` (**default**, most *weekly* headroom), `least_used_5h` (most 5-hour headroom), `waterfall` (configured order, skipping spent), `manual` (`default_account`, strict — it returns the chosen account **even when spent**, since quietly rotating away defeats the only reason to pick that mode). The least-used pair differ only in which window `pctOf` reads, via `rankWindow` → `Usage.Pct(Window)`. **Weekly is the default because the two windows fail on different timescales**: a 5-hour bucket refills this afternoon, so losing that race costs an hour, while a weekly bucket spent on Tuesday is gone until the following week — and ranking on the fast window lets every account's slow window drain in lockstep, which is the state that takes the whole fleet down at once. The pre-split `least_used` survives as an **alias, not a value**: `ParseStrategy` resolves it to weekly (same as unset) and `Strategies` — the ordered set both pickers offer — deliberately omits it, so cycling can never land on it. Mapping it to the 5-hour variant instead was rejected: it would make the *presence* of the key change behaviour, so the same file would behave differently depending on whether it was ever written. `StrategyLabel`/`StrategyLabels` live in `claudeaccount` for the same reason `Window.Name` does — the Settings cycler and the accounts dialog both render them, and two copies of the strings is how they stop agreeing. Selection-only: the accounts list, move picker and header readout still show the 5-hour figure regardless of strategy. Sessions are **pinned at creation**: Claude's prompt cache is per-account, so re-picking on every restart would drop the very thing a restart preserves. Forks **inherit** the parent's account (`forkSessionMsg.account`) — a fork resumes the parent's conversation and must authenticate as its owner.
- **A missing login is evidence; every other poll failure is not.** `FetchUsage` returns `ErrNotLoggedIn` for 401/403, the poll stamps `Usage.LoggedOut`, and `Select` drops those accounts via `dropLoggedOut` ahead of every strategy including `manual`. Without it an account with no login never gets a reading, so `pctOf` scores it at `unknownPct` (50) — which beats a healthy account at 59% and hands **every** new session the one account that cannot run, with no error anywhere. Categorically unlike *spent*, which `Select` still returns (soonest to reset) because a wait ends; a missing login doesn't, so emptying the candidate list is right and the caller falls back to the ambient login. `LoggedOut` is **live state on `Usage`, never persisted** — an account heals the moment it is logged in again (`handleAccountLoggedIn` replaces the usage entry outright, so the fix isn't invisible until the next poll). Shown as `✕ logged out` in the accounts dialog and the header readout, which renders it even with no reading at all.
- Restart **heals a pin that can't run** (`healAccountBeforeRelaunch`, called from `restartSession` and `resumeSelected`): if the pinned account was removed, is logged out, or is spent, the session is re-picked, persisted via `UpdateAccount` and announced in a toast — pinning protects a prompt cache, and there is no cache worth protecting on an account that can't answer. An **unpollable** account is left alone: fleet failing to reach Anthropic is not evidence against the login, and healing on it would rotate the whole fleet during an outage. A heal forces the **full `Restart()` path, never `RespawnClaude`** — `respawn-pane -e` layers over the environment tmux created the session with, so a move *to* the ambient login (which sets no variable) would inherit the old dir.
- Manual move: `.` → **"Move to Account…"** (`move_account` → `openAccountPicker`), a row-anchored dropdown (`internal/ui/account_picker.go`) built on the context-menu overlay pattern. - Quota comes from `GET https://api.anthropic.com/api/oauth/usage` — the cheap official route, available because a real login carries `user:profile`. Reading it consumes **no** message quota. The bearer is read out of that dir's Keychain item at poll time and never stored (`accessToken`, `security find-generic-password -w`). Values are already percent (0..100), unlike the rate-limit headers the old probe parsed, which were fractions — exactly one of the two ever needed scaling. Polled on the worker's heavy pass, throttled ≥180s per account — **except across a window's own reset** (`Usage.StaleAfterReset`), where the throttle is broken because the numbers have stopped describing the bucket they were read from: a spent account otherwise keeps reading spent for three minutes after it came back, with its countdown already at zero, which is exactly when its owner is watching. Bounded below by `AttemptedAt`, not simply "the reset is in the past" — a poll that *fails* at the boundary moves `AttemptedAt` past it, so the account backs off normally instead of retrying every tick against an endpoint that just refused. Failure is recorded rather than raised, so an unpolled account reads as *unknown*, not spent, and `least_used` degrades into waterfall order.
- **`GuardConflictingAuth` matters more here than it did before.** A config dir's login sits at the *bottom* of the precedence order, so an ambient `ANTHROPIC_AUTH_TOKEN` or `ANTHROPIC_API_KEY` inherited from the user's shell silently overrides **every** account at once. tmux `-e` can add variables but not remove them, so a session can't scrub what it inherits — refusing loudly is the only honest answer. (fleet's own helper commands do scrub, via `configDirEnv`: fleet is often launched *from* a fleet session, and an inherited credential would make `claude auth status` report the wrong account.)

- Header readout (`internal/ui/accounts_header.go`, Appearance cycler `account_usage_style`): per-account usage top-right, **both windows every frame**, 5-hour first, each carrying **when that window resets** — a weekly figure without its horizon is unactionable. Two styles: `split` (default) gives each window its own countdown (`yuval 12%(2h) 34%(5d)`), `grouped` pools them (`yuval 12%/34% (2h/5d)`), `off` hides the strip. **It replaced a strip that moved on its own**: the readout used to show one window at a time and swap every 6s off the wall clock, *and* pick one of six densities by measuring what the breadcrumb left over — so a corner of the screen changed on a timer and reshaped whenever the cursor moved to a longer session title. Nothing here reads the clock now except the countdowns (`TestReadoutIsStableOverTime` renders at three offsets and demands byte-identical output). **Nothing names the windows — order does**, which is why 5-hour leads in every style and state; the countdowns cannot stand in for it, since a weekly window about to roll over reads `3h` exactly like a 5-hour one. The two styles are the **same width by construction** (four tokens plus five characters of glue either way), so neither is called "compact" and the fit ladder is style-independent — a narrower style would put the grouping back under the breadcrumb's control. That ladder is now **two steps**: drop the account names, then render nothing (it never falls back to the *other* style, for the same reason). A spent window is **not** special-cased into `spent <countdown>` any more — `quotaStyle` already paints anything at `ExhaustedPct` red, the same threshold `Select` stops handing the account out at, and the countdown sits beside it, so the state is legible without the chip changing shape *and* the other window's figure survives instead of being hidden. A reset that has **already passed** renders `now` rather than dropping the parenthetical (`100%(now)`): a countdown that vanishes at the moment it reaches zero leaves a red figure with no horizon in the one state where the horizon is the whole answer, and it is the chip changing shape on a timer. `now` is a claim that a fresh figure is one tick behind it, so it is **gated on `Err == nil && reset.After(FetchedAt)`** — neither the wall clock nor the reset time can promise that on their own. A *failing* poll advances `AttemptedAt` past the reset, which is what bounds the throttle break, so across an outage spanning a reset nothing re-polls and the strip would read `34%(now) 71%(now)` for its whole duration; and a poll that *succeeds* while returning an already-past reset (a 5-hour block is anchored to its first message, so a lapsed one can report its old `resets_at` for hours) is answering about a window it has already left. Both fall back to `""` — the bare figure this rendered before the countdown existed. An unknown reset drops as it always did. `✕ logged out` still takes the whole chip (no numbers to show) and renders even with no reading at all. In `grouped` the countdown parenthetical is **all or nothing** — pooled countdowns make `12%/34% (5d)` unreadable — while `split` drops each independently. Hidden below two accounts, or when even the nameless form would overflow and push the What's New badge off its corner. `account_usage_style` supersedes the legacy `show_account_usage` bool, of which only `false` migrates (→ `off`); the Settings cycler clears it on write.
- Per-origin allowlist (`allowed_accounts` config, keyed `origin:<key>` — the same keyspace as `collapsed_groups`/`snoozed_groups`; empty = all allowed). Deliberately **not** `.fleet.json`, which is committed — account policy is personal. Chosen over a per-origin *pin* because it composes with rotation: a pin has no good answer when its account is spent, while an allowlist does. Edited from `.` on an **origin header** → **"Allowed Accounts…"** (`internal/ui/allowed_accounts.go`), a row-anchored checkbox dropdown on the account picker's overlay pattern. Origin rows only: the key is per-origin, so offering it from a session or worktree row would put an origin-wide rule behind a control that looks like it acts on the row you're standing on. **Ticking every account deletes the key rather than storing the full list** (`config.SetAllowedAccounts`) — the two read identically today, but a stored list silently locks out the *next* account added, with nothing on screen to explain it; `a` toggles all, so it doubles as "remove the restriction". Zero ticked is **refused, not saved** (same rule as `SnoozeDialog`'s unparseable box): an empty list already means unrestricted in config, so saving it would do the opposite of what ticking nothing looks like it asks. A logged-out account stays **tickable here** — deliberately unlike the move picker, which can't move a session *onto* a dead login: this is policy, not availability, and "client work runs on the work subscription" stays true while that subscription is logged out. Rows are built from `Store.List`, so an email naming a removed account has no row and is dropped on save — opening and saving **heals** the stale-allowlist state `resolveAccount` refuses new sessions on. That heal is why the menu guard is **asymmetric**: `only one account` dims the row at `Len() == 1` *only when the origin has no stored allowlist*. Removing an account never prunes the allowlists naming it (`accountRemoveMsg` clears `default_account` and nothing else), so removing down to one account can leave an origin pointing at an account that no longer exists — which `resolveAccount` answers by refusing every session there, with the one UI that could clear it dimmed and `config.json` as the only escape. Deliberately **not** fixed by pruning on removal: empty *is* unrestricted, so pruning to empty silently widens the policy, and `AllowedConfigured`'s doc comment names "an account since removed" as precisely the case where falling back is "the one genuinely wrong answer". `openAllowedAccounts` mirrors the guard exactly, so a lit row can't dead-click and a dimmed one can't be reached another way. Sessions already pinned to a now-disallowed account are left alone; the allowlist governs *selection*, and the prompt cache it protects is per-account.

- OpenCode status: driven entirely by a generated TS plugin (no pane scraping); same agent-neutral `fleet hook-handler` pipeline. Unlike Claude/Codex declarative hook JSON, OpenCode's hook mechanism is a JS/TS plugin, so fleet writes `~/.config/opencode/plugin/fleet-status.ts` (`InjectOpenCodePlugin`, only when `opencode` on PATH; the resolved fleet binary path is baked in). The plugin's `event` hook maps OpenCode-native bus events → fleet statuses via `spawnSync` (synchronous so the final status flushes before OpenCode exits, and ordering is preserved): `session.status{busy}`→running, `session.idle`→finished, `question.asked`/`permission.asked`→waiting, `question.replied`/`question.rejected`/`permission.replied`→running. **Both prompt families are live in OpenCode 1.14.x and are not interchangeable**: `question.*` is the AskUserQuestion tool prompt, `permission.*` is a tool-permission prompt (only fires if the user set `permission: ask`; OpenCode defaults to allow-all). Watching only one is the stuck-at-running bug — the branches are additive, never a swap. The `*.replied`/`*.rejected` listeners are belt-and-braces: OpenCode publishes `session.status{busy}` right after a reply anyway. Sub-agent sessions carry a `parentID` and are filtered so they don't flip the root session's status. No dir-trust seeding needed (OpenCode has no trust gate). No SessionEnd → `dead` from tmux pane-death. `UpdateStatus` routes OpenCode through `applyHookStatus` (shared with Codex); no pane heuristics run.
- Codex trust: dir-trust pre-seeded to `~/.codex/config.toml` (`[projects."<path>"] trust_level="trusted"`, via `EnsureCodexDirTrust`) before launch; hook-trust is a one-time global TUI prompt the user accepts on first Codex launch (persists in config.toml `[hooks.state]`).
- Session resume: captures the agent's session_id from hooks, uses `claude --resume <id>` / `codex resume <id>` on restart
- Editor: config.editor > $EDITOR > "code" (VS Code). `internal/editor` resolves the name to a command: CLI launcher on PATH if there is one, else `open -a <App>` against the installed bundle. That fallback is what makes JetBrains IDEs (GoLand, PyCharm, IntelliJ, …) work — Toolbox doesn't install `goland`/`pycharm` shims unless asked, so PATH-only lookup failed with "executable not found". Bundles are prefix-matched (`PyCharm Community Edition.app` → `pycharm`) across `/Applications`, `~/Applications`, and `~/Applications/JetBrains Toolbox`, scanned once per launch. The Settings editor cycler offers only editors this machine can actually launch (`editor.Available()`), so a preset can't be a dead option. Flags (`code -n`) are a CLI-only contract: a spec carrying them with no launcher on PATH errors rather than silently dropping them.
- Themes: fleet-pink (default, flagship brand accent `#dc88c0`), tokyo-night, catppuccin-mocha, rose-pine, nord, gruvbox — configurable via settings (S key)
- Settings dialog: S key opens a master-detail overlay — category rail (Appearance / Behavior) on the left, that category's settings on the right; `tab` switches panes, `j/k` move, `←→`/`h/l` cycle a value, auto-saves on `esc`. The **Appearance** category renders a live mock-sidebar preview (synthetic data via `RenderSidebarPreview` → the real `RenderSidebar`, so it can't drift) and holds: Theme, Status style (icon/bar), Agent icons, Slot badges, Account usage (split/grouped/off), PR badges, Dirty marker, Status pills, Header counts, Chevron style (triangle/plusminus), Density (normal/compact). Behavior holds editor, tick, auto-name, auto-update, copy .claude, confirm before restart, drawer height (rows, capped at the 14-row body max), origin forget removes worktrees, enter mode, telemetry, default agent, idle-session suspend (off/light/balanced/aggressive).
- Display toggles: each Appearance toggle is a `*bool`/string config field with a default-on getter (`config.go`) feeding a package global in `styles.go` (`ShowAgentGlyphs`, `ShowStatusPills`, `ShowPRBadges`, `ShowDirtyIndicator`, `ShowSlotBadges`, `ShowHeaderCounts`, `ChevronStyle`, `SidebarDensity`) — the same pattern as `StatusIndicatorMode`. Globals are synced from config via `ApplyDisplayConfig(cfg)` in `NewHome` (startup) and after each Appearance change; the sidebar `render*` funcs read them at render time.
- First-run onboarding: on first launch, after the analytics consent prompt, a one-time theme picker (`internal/ui/onboarding.go`, gated by `display_onboarding_seen` config flag) shows the theme cycler beside an annotated sample sidebar that teaches how to read status dots, agent glyphs, branch, worktree, dirty `*`, and PR badge. `enter` keeps the previewed theme; `s`/`esc` reverts and skips. Either way it's marked seen.
- Telemetry (`internal/analytics`): three modes via `telemetry_mode` config (`full`/`minimal`/`off`; read through `config.GetTelemetryMode`, which migrates the legacy `telemetry` bool — true→full, false→minimal). **full** = usage events tagged with git name/email (PostHog person profile; distinct_id = git email). **minimal** = anonymous only: just `app_started` (version + mode) and a per-day `app_active` heartbeat keyed on the device hash — no identity, no people profile: anonymous events set `$process_person_profile=false` so the device still counts as a unique user (DAU) on the device-hash distinct_id; every other `Track/Gauge/Distribution/SetUserProperties` no-ops (gated on `Client.mode` in `analytics.Init`). **off** = disabled client, nothing sent. First-run consent prompt (`internal/ui/consent.go`): accept → full, decline → minimal (the dialog discloses that declining still sends the anonymous ping); `off` is Settings-only (Behavior category, 3-way cycler). Env `FLEET_TELEMETRY_DISABLED`/`DO_NOT_TRACK` force off regardless of mode. `analytics.Heartbeat()` (fired on the UI tick, rate-limited to once per calendar day in-memory) keeps DAU accurate for long-running instances that rarely restart; it runs in both full and minimal. `SyncEnabled` tears down + re-inits the live client when the mode changes in Settings — detaching the old client synchronously (so `Init` installs the new one) but flushing it on a goroutine, since Settings-close runs on the Update() thread. Backend is PostHog via the `posthog-go` SDK (built in `newSink`, `analytics.go`), which owns its own batching worker; the project (capture) API key is embedded like the old ingest token — write-only, ingest-only — with `FLEET_POSTHOG_KEY`/`FLEET_POSTHOG_HOST` env overrides. A build with the key stripped (`projectAPIKey` blank) creates a disabled client and sends nothing. The SDK's `Enqueue` **blocks**, so `Client` fronts it with a drop-on-full queue (`queueSize` 256) drained by a background goroutine — that's what keeps `Track`/`Gauge` safe to call from `Update()`; a full queue drops the event rather than stalling the UI. Quit flushes via `Shutdown` (bounded by `shutdownTimeout`, 2s). The SDK's own `Debugf`/`Logf` are **dropped, not forwarded** (`phLogger`): they log the serialized message, whose `distinct_id` is the git email in full mode, and `debug.log` is what the bug-report flow pastes into a public issue — only `Warnf`/`Errorf` (counts + error strings, no payloads) reach the log, at `Warn` so broken telemetry is visible without `FLEET_DEBUG`.
- Report dialog (`!`): a **type picker first** (Wrong status / Bug / Feature), then a form sized to the kind — each files with its own label (`bug` / `bug` / `enhancement`) and its own body, so a feature request carries no debug log and a status complaint can't land as an undiagnosable generic bug (the #157 outcome). The picker is a stage of the existing `BugReportDialog`, not a new dialog, so it inherits every registration (`modalOpen`, `routeToModal`, `renderBody`, `SetSize`). Esc on a form returns to the picker; Esc on the picker closes.
- Wrong-status reports (`internal/ui/statusreport.go`): the capture fires **at the `!` keypress**, not at submit — status is a moving target, and by the time a description is typed the session may have self-corrected, so re-reading then would freeze a state nobody is complaining about. `openBugReport` (app.go) shows the dialog and returns the capture `tea.Cmd`; it lands via `reportSnapshotMsg` → `SetSnapshot` (ignored unless the arriving capture's session id matches the form's). The shown status and title are likewise read once at keypress. The form adds an expected-status cycler (`running/waiting/finished/idle/error` — not `starting`, transient, nor `suspended`, user-initiated) that **starts unset and refuses submit**, same rule as `SnoozeDialog`'s unparseable box; the footer names whichever field is missing. Body is **two tiers**: the signals table (hook status/event/age, `pane_detected` vs `tui_shows`, worker stalled, `claude_log.advanced_past_hook`) always ships and holds no user content; the screen excerpt (last 40 pane lines) plus the session-filtered debug log ship behind `ctrl+p`, **on by default**, previewed in the dialog above the toggle so the default is visible rather than silent. Switching it off hides the excerpt from the preview too (a preview that outlives its checkbox is the ambiguity previewing was meant to remove) and drops the *global* debug log **and config.json** from the shared diagnostics block (`FormatEnvironmentMarkdown(includeLogs)`) — otherwise the toggle would remove one log and smuggle a wider one back in, and config carries `default_project_path`, confidential in its own right when client names live in directory names.
- Status-report body is built by **allowlisted field reads** off the snapshot map (`metaSub`/`metaString`), never `json.Marshal` of it: `snapshot.json` embeds `hook.file_contents.user_prompt`, the reporter's verbatim prompt, which the dialog never shows them. `TestBuildStatusReportBody_NeverLeaksUserPrompt` guards it. Governing rule: **nothing ships that the dialog didn't show or the checkbox didn't name.**
- `captureStatusSnapshot(..., persist, copyTranscript bool)`: `Shift+D` passes `true, true`; the `!` path passes `false, false`. **`persist=false` touches the filesystem nowhere** — no dir, no `snapshot.json`, and crucially no `writeGoroutineDump` (`runtime.Stack(all=true)` pauses every goroutine, which must not sit on a hot interactive key). `!` fires a capture on every press, before a report kind is chosen, so persisting would fill `~/.config/fleet/snapshots/` with cancelled dialogs and feature requests and break the invariant the `debug-status` skill leans on: the newest dir there is a deliberate `D` capture. Nothing is lost — the issue body is built from the returned values, never read back off disk, and the two files that exist only on disk (`pane_raw.txt`, `goroutines.txt`) are never published anyway.
- Async capture is matched by **session id**, not visibility (`snapshotResult.sessionID` vs `statusReportForm.sessionID`). `!` on A, `esc`, `!` on B are both visible status forms, so an id-blind guard lets A's slow capture land in B's form: the issue would be headed with B's title and status while every signal, the excerpt and the log came from A — publishing A's screen, which that dialog never previewed.
- Submit gating runs through **one** function, `submitBlocker`, consulted by both the Enter handler and the footer so the key can't act on a state the footer calls unready. It blocks while the capture is in flight (`!captured && err == nil`) — submitting then would emit "the capture failed or the session had no live tmux pane", a false cause, on exactly the undiagnosable report this flow exists to prevent. A capture that genuinely *failed* still submits: there the line is true.
- Pane excerpts and titles truncate with `ansi.Truncate`, never the byte-based `truncate` in `bugreport.go`. Pane lines are dense with 3-byte box-drawing runes (`│ ╭ ─ ❯`), so byte slicing cuts at roughly a third of the intended columns and can split a rune — the excerpt the reporter is asked to approve wouldn't match their screen, and invalid UTF-8 can reach lipgloss.
- `sanitizeHome` (statusreport.go) is the single home→`~` rewrite for everything bound for a public issue, **including issue titles**. A body that sanitizes while its title publishes `/Users/<name>/…` verbatim leaks on the one line GitHub shows in search results and notification mail.

- Action log: ring buffer (max 100) of user actions (attach, delete, restart, editor, approve, etc.) for "steps to reproduce"
