V2 — RESILIENCE-FIRST

What the critics changed

The original brainstorm was biased toward dev-velocity (CI, registries, tests, refactors) and missed production resilience entirely. Both critics — independently — flagged the same omissions.

The big rebalance: half the original Tier S/A is paint for a solo dev pre-distribution. What actually matters: db corruption protection, daemon-dies-while-Mac-attached, distribution path. None were in V1.

  • Promoted to Tier S: daemon singleton lock, db backup + integrity check, Mac top-level reconnect, crash-loop guard, fleet doctor, Sparkle path scaffolding
  • Demoted to Later: action registry, AppModel split, app.go decomposition, snapshot tests, theme catalog, daemon-side analytics
  • Defer (cargo cult): mprocs / watchexec / act / mise, swift-snapshot-testing, full OpenTelemetry, gofumpt + goimports-reviser, mockery
  • Split decisions to flag: protovalidate (transformative vs cargo cult), swift-dependencies (real DI vs TCA-adjacent), request IDs (promote vs defer)

Critic 1 — The Pragmatist

Lens: solo dev, pre-distribution, every infra hour is a feature hour lost.

Verdict: Original top-5 = ~2 weeks. Cost of skipping all 5 for 3 months = ~5–8 hours. The math doesn't work.

  • Action registry is "exactly the kind of premature abstraction your own CLAUDE.md warns against"
  • OTel + protovalidate + swift-dependencies = "fancier slog" / cargo cult for a one-person shop
  • What's missing: SQLite schema-version + write-conflict audit

Critic 2 — The Veteran

Lens: shipped two-stack Go-daemon + Mac apps before; knows what bites at month 6.

Verdict: Brainstorm is "dev-velocity, not production-resilience." The biggest 6-month risks aren't on the list at all.

  • No daemon singleton lock → two daemons can briefly open the same SQLite. #1 silent corruption vector.
  • Mac has stream-level reconnect but no top-level transport reconnect. Daemon crash = Mac app dead until relaunch.
  • Distribution (Sparkle) should be a column, not a row — it gates "do you have Mac users at all"
TIER S Resilience first — what'll bite before any dev-velocity issue does

1.Daemon singleton lock + db integrity + nightly backup NEWGo

PrepareSocket in internal/daemonsrv/socket.go:38-60 handles the socket file, but there's no flock on state.db. If two fleet daemon invocations race (or daemon + --standalone TUI race), both briefly open the same SQLite. modernc/sqlite WAL with busy_timeout=5000 serializes writes, but you've got two SessionService instances racing tmux state. Plus: no PRAGMA integrity_check on open, no rotating backup.
Fix
flock on state.db + pidfile, integrity_check on open, copy state.db → state.db.bak-<date> on daemon start (keep last 3). Sub-MB file.
Why it pays off — ~1 day
The only failure mode on this list that can destroy user data. Everything else is recoverable.

2.Mac top-level reconnect + crash-loop guard NEWSwift

DaemonClient.swift:22-71 exits the withGRPCClient closure on disconnect and sets .disconnected — user must relaunch the app. Stream-level reconnect in StreamConsumers.swift only handles in-stream errors. If fleet daemon crashes, the Mac app is dead until quit-relaunch. P0 before any user sees this. Also: internal/daemonclient/autospawn.go:30-46 has no crash-loop guard — daemon dying repeatedly = infinite respawn from every launch.
Fix
Wrap DaemonClientRunner.run in a top-level retry Task with exp-backoff. ~50 lines. Add crash-loop guard: if daemon dies 3× in 60s, surface the actual crash and stop respawning.
Why it pays off — ~0.5 day
Without this, the Mac app is a demo, not a shipped product.

3.fleet doctor subcommand NEWGo

Single command that prints: daemon alive? socket path? db size + integrity? tmux sessions found? hook files in dir? config dir perms? $PATH has gh? Chrome NMH installed?
Why it pays off — ~0.5 day
You'll write this anyway the third time a user hits a bug. Build it once, save N support cycles later.

4.make dev + make reset + tiny Swift CI Repo

Scoped down from V1. No mprocs. Just a bash script that runs daemon + Mac watcher. make reset is 3 lines (backup + rm ~/.config/fleet/). Mac CI = commit Package.resolved + 6-line GH Actions workflow running swift build + swift-format lint. That's it.
Why it pays off — ~30 min
Three-process dev loop becomes one terminal. make reset used weekly. Both critics agree this is real.

5.Sparkle path scaffolding now PROMOTED B→SSwift

Veteran flagged: Sparkle in Tier B treated it as quality-of-life. It isn't — it's the gate to "do you have Mac users at all." Without auto-update, every bug fix means a manual download. The day you put the Mac app in front of someone, you need it.
Fix (scaffolding now, ship later)
Add Sparkle dep + .app bundle scaffolding + xcodebuild archive step in Makefile. Don't ship updates yet — but stop pretending the app is "almost a real app."
Why it pays off — ~1 day
Distribution is the unlock. Every other Mac improvement is gated on this.

6.Snapshot proto unification Both

From V1: two snapshot formats (TUI dir-of-files vs Mac markdown blob). Define a Snapshot proto, both clients write the same shape, extend debug-status skill to handle either source. Pragmatist gave this 7/10 — small effort, real payoff.
Why it pays off — ~2 hours
When Mac users hit bugs, the AI debugging workflow you built for the TUI just works.
TIER A High leverage, near-term — pick up after Tier S lands

7.Request IDs + per-client trace field Both

Critics split: pragmatist says 3/10 urgency (you've triaged 0 cross-client bugs so far); veteran says promote because every support email is detective work without it. With a real TUI user base on Homebrew + Mac app coming, side with veteran. Just don't over-build: request_id UUID + client field in every log line. Skip OTel for now.
Why it pays off — ~1 day
First bug from a real user, you'll know which process did what.

8.Schema versioning + migration playbook NEWGo

Pragmatist's catch: you already have internal/migration/migrate.go for the rename. Mac app now reads same db via daemon. What happens when a user with v2.1.0 (TUI-only) pulls down a daemon binary that opens their db with a new column? Add schema_version table + a one-page playbook for column additions.
Why it pays off — ~0.5 day
Prevents the second category of "destroys user data" bug.

9.Kill-daemon-while-attached chaos test NEWRepo

Pragmatist's ask: a deliberate test that kills the daemon mid-stream while Mac is attached. Confirms #2 actually works. Could be as simple as a shell script: launch daemon, launch Mac, kill -9 the daemon, watch Mac recover. Manual today, scriptable later.
Why it pays off — ~0.5 day
Verifies the fix; documents the contract.

10.swift-async-algorithms adoption Swift

Both critics flagged this as the one Swift package that's genuinely useful (not cargo cult). Cleaner stream consumer in StreamConsumers.swift, free debounce on filter input via debounce/throttle/merge.
Why it pays off — ~1 day to adopt
Replaces hand-rolled timer patterns. Code shrinks.

11.Logging vocabulary doc (skip the sweep) Both

From V1, scoped down. Pragmatist: "doc is fine (30 min), sweeping 247 logger calls is paint." Agree. Write a one-pager: session_id, request_id, rpc, client, err. Future code follows it; existing code stays.
Why it pays off — ~30 min
Substrate for future log search without retroactive churn.
FRAMING QUESTIONS The veteran's "questions you should be asking but aren't"

Do TUI and Mac app share state, or share tmux?

Right now they share state via the daemon: same SQLite, same session list. But nobody runs TUI + Mac simultaneously on the same machine — the Mac app is the TUI's successor, not its peer.

If you decided "they're independent apps that both happen to drive tmux," half the Tier S evaporates: no action registry, no shared-db corruption, no daemon SPOF. The flip side: future CLI ecosystem (fleet api, MCP servers, Raycast extension) loses its integration point.

Worth a day writing down: "why do we have a daemon, and what does each consumer actually need from it?"

Is the in-process service fallback worth maintaining?

cmd/fleet/main.go:318-347 — TUI degrades gracefully to in-process service.SessionService if daemon spawn fails. Mac doesn't. This is a contract surprise: same backend, different failure semantics.

Worse: every new daemon-side feature (CreateWorkspace, soft-delete tombstones) gets implemented twice (in SessionService + daemonclient.Client). Same drift problem as the action registry, invisible because both are Go.

Pick a side: kill the fallback (commit to daemon-always) OR commit to always-fallback (Mac learns to spawn its own daemon). The current both-paths arrangement is the worst of both worlds.

When does Mac distribution start?

Sparkle, codesign, notarize, DMG. Until one person who isn't you can install + auto-update the Mac app, all the rest of this is academic.

Distribution should be a column in this brainstorm, not a row. Every Tier S item is worth asking: "does this matter before or after first external user?"

Trigger: AppModel stops changing weekly (probably slice 6–7). Pragmatist: "testing churning code is throwaway work." The simple protocol DaemonMutating + FakeDaemonClient is the right shape — no swift-dependencies needed.

Theme catalog / SwiftUI snapshot tests / Activity inspector Swift

Trigger: design churn slows. Veteran on snapshot tests: "great for design-heavy apps; you have 6 sheets and Apple Previews give you 80%." Activity inspector is a feature wearing infra clothing.

Daemon-side analytics, stricter linters, sentinel errors, skills Go

All real. None bite this quarter. Revisit when current sprint settles.
